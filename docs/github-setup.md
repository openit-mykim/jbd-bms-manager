# GitHub Repository Setup

Repository: `openit-mykim/jbd-bms-manager`

This document defines the intended GitHub configuration. Some settings are repository-admin UI settings and should be applied after baseline CI is present.

## Repository basics

Recommended settings:

- Visibility: Public
- Default branch: `main`
- Issues: Enabled
- Projects: Optional
- Discussions: Optional; not required for initial development
- Wiki: Disabled unless there is a later user-facing documentation need
- Allow merge commits: Enabled for upstream provenance merges
- Allow squash merging: Enabled and preferred for normal feature PRs
- Allow rebase merging: Optional
- Automatically delete head branches: Recommended after normal PR merge

## Main branch ruleset

Do not enable required CI checks until the OpenJBD baseline and workflow are imported and a successful run exists.

After Phase 0, configure `main` with:

- require pull request before merge
- require conversation resolution
- require status checks
  - unit test job
  - debug APK build job
- block force pushes
- block branch deletion
- allow owner/admin bypass for emergency recovery
- no strict linear-history requirement, because upstream sync may intentionally use merge commits

If working alone, requiring an external approval may block automation. In that case, keep PR review as an agent/process rule rather than a hard GitHub rule until another reviewer is routinely available.

## Merge policy

Normal development:

- prefer squash merge
- one concern per PR
- delete merged task branch

Upstream sync:

- merge commit is allowed when it preserves meaningful upstream ancestry
- use branch `chore/sync-openjbd-YYYYMMDD`

## GitHub Actions

After source import, retain or adapt the upstream Android debug CI so pull requests run at minimum:

```text
./gradlew testDebugUnitTest
./gradlew assembleDebug
```

Upload debug APK as an artifact for manual device testing.

Later release workflow:

- trigger on version tags such as `v0.1.0`
- use repository secrets for signing material
- never commit keystore or signing password
- publish checksums with release artifacts

## Security settings

Recommended:

- Secret scanning: Enabled where GitHub plan supports it
- Push protection: Enabled where available
- Dependabot alerts: Enabled
- Dependabot security updates: Enabled after baseline dependency health is understood

Do not add automated dependency PRs that flood the repository before the Android baseline is stable.

## Issues and project phases

Top-level roadmap work is represented as numbered issues. The active source of truth remains `PROJECT_STATUS.md` + `docs/development-plan.md`.

Issues are useful for:

- phase-sized implementation work
- reproducible bugs
- protocol compatibility research
- device validation records
- release blockers

Do not create an issue for every tiny subtask generated by an agent; Paseo workspaces can carry those execution-level tasks.

## Fork/upstream model

This repository is not a GitHub-native fork. This is intentional because it has its own product identity and governance.

Use local remotes:

```text
origin   -> https://github.com/openit-mykim/jbd-bms-manager.git
upstream -> https://github.com/gytxtx/OpenJBD.git
```

Initial and ongoing sync rules are in `docs/upstream-sync.md`.

## Agent handoff requirement

A Hermes Agent receiving only this repository URL should be able to determine:

- current phase from `PROJECT_STATUS.md`
- rules from `AGENTS.md`
- Paseo configuration from `paseo.json`
- next implementation step from `docs/development-plan.md`
- upstream relationship from `docs/upstream-sync.md`
- testing expectations from `docs/testing.md`

Repository changes that break this handoff model should be treated as architectural changes and documented explicitly.
